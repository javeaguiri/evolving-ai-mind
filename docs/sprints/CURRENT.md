### Track F — IntentMap Structural Refactor

**F2 — `create_domain` help-command generator assumes one root table per domain — ✅ DONE (2026-07-06)**
- Raised alongside F3 while diagnosing the misleading `/help budgets_expenses` output — the domain actually has 4 independent root entities (`PGD_SpendingCategories`, `PGD_Budgets`, `PGD_Expenses`, `PGD_RecurringExpenses`, confirmed via live `PGC_EntitySchema`/`PGC_Schema` — all 3 non-category tables reference `PGD_SpendingCategories` via `SET NULL`, not `CASCADE`, so none is a "child" under the `rootTables` computation), but `create_domain` step 18's `commands` builder picked exactly one "root table" (most incoming FKs, or `tables[0]`) and built all 5 generic CRUD lines against only that one, silently hiding the other 3 entities from `/help`.
- Confirmed the underlying generic workflows (`add_entity`/`list_entity`/etc.) already handle this correctly — Sprint 6's entity-resolution chain (step 1a/1b/1c in `add_entity`) already auto-resolves which entity a bare `/m add budgets_expenses <description>` refers to via a lightweight LLM call when the domain has more than one `PGC_EntitySchema` row. The gap was purely informational: `/help` never told the user this multi-entity capability existed.
- Fix: hoisted the existing `rootTables`/`fkChildNames` (CASCADE-FK-based) computation — already used later in the same step to build `entitySchemas` — to run *before* the `commands` builder, and reused it there instead of duplicating a separate heuristic. When `rootTables.length > 1`, each of the 5 generic CRUD lines' `description` now appends the real entity names (e.g. "this domain has multiple record types: Budget, Spendingcategorie, Expense, Recurringexpense — the system infers which one from your description, or you can specify it explicitly"), using the exact same `toEntityName` naming the entity schemas themselves use, so the names shown match what a user would actually need to type. Single-entity domains (the common case — flashcards, recipes) get zero output change, verified by direct test against both shapes before touching the seed file. The bulk-add example (separate "most-referenced table + its FK-child" heuristic, unrelated to `rootTables`) is left untouched — it already demonstrates one genuinely useful compound-insert pattern and was never meant to be exhaustive.
- Edited via a precise byte-level substring replace (matched the exact old `expression`/`description` JSON string, confirmed single occurrence, replaced only those two fields) rather than a whole-file JSON re-serialize — an initial attempt using `JSON.stringify(seed, null, 2)` reformatted an unrelated step elsewhere in the file (object-per-line instead of inline), reverted before committing. `docs/code-review-checklist.md`-style lesson: never round-trip a large hand-formatted JSON seed file through a generic serializer for a single-field edit.

### Track G — Raw Input Parsing + serv_insert Consistency

**G1 — `step-executor.mjs` — serv_insert bulk always returns array**
- The bulk insert path returns `resp.rows ?? { tableName, inserted: row.length }`. When SERV returns a single-item object instead of an array (one-row bulk), downstream js_transform `.forEach()` / `.map()` calls crash.
- Fix: `outputValue: Array.isArray(resp.rows) ? resp.rows : resp.rows ? [resp.rows] : []` — always array.

  - **Within one Lambda invocation**, `runReasoningLoop`'s `while (turnCost < prefs.turn_limit)` is provably bounded — every branch (read tool, write tool, gated tool, trigger tool, unknown action, `respond`) either increments `turnCost` by ≥0.5 or breaks out of the loop entirely; there is no path that loops without doing one or the other. **I3 — Uncertain-key cascade suppression — DONE**
- User caught a real false-positive risk: the smoke test does a single forward pass over the step array — it never unrolls loops. Flat-loop-pattern workflows (e.g. flashcard quiz: test each of 10 cards 3 times before advancing to the next subset, all subsets before a `human_gate`) depend on accumulator state a single pass can't reconstruct, so an accumulating `js_transform` can throw against placeholder mock data even when the workflow is correct.
- Before this fix: when a `js_transform` threw/timed out/void-returned, its `output_key` fell back to `{}` in `mockState` — a downstream step consuming that key via a bare `{{key}}` reference would then get shape-checked against `{}`, almost always failing, producing a **hard failure caused by an inconclusive upstream mock, not a confirmed defect**.

The upstream step's own issue (`js_transform_runtime_error`, already a soft warning) is still reported — only the misleading cascaded downstream hard failure is suppressed. Absence of confirmation is not proof of a defect.
- New unit test reproduces the exact scenario (a `js_transform` throwing on unmocked accumulator state feeding a `serv_upsert.rows` field) and confirms no `serv_input_shape_mismatch` is raised while the upstream warning still is. 373/373 unit tests pass.
