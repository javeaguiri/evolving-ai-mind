### Track F — IntentMap Structural Refactor

**F1 — `PGC_IntentMap` — one row per phrase — ✅ DONE (2026-07-06)**
- **Scope boundary (deliberate):** applies only to workflow-linked rows (`workflow_id IS NOT NULL`) — the set `create_workflow`'s own registration step manages. System-seeded rows (`workflow_id IS NULL`: `create_domain`, `help`, `create_domain`'s generic per-domain CRUD rows for `add_entity`/`list_entity`/etc.) are untouched — they're managed by `seed_PGC_IntentMap.json` + `upsert-intent-map.mjs`, which matches/upserts on `intent_category` alone; splitting those into multiple rows per `intent_category` would break that script's idempotency key (it would silently re-join a split row back into one on the next upsert run) and requires its own migration — flagged as a related follow-up (F1b), not done here.
- Schema: added `PGC_IntentMap.source` (nullable text, `CHECK (source IS NULL OR source IN ('user','auto','name'))`) via `dev_scripts/migrate-pgc-intentmap-source-column.mjs` — also syncs `PGC_Schema`'s registry row and updates the bootstrap template (`src/serv/templates/pgc/PGC_IntentMap.json`) so a fresh install matches. `docs/arch-data.md` updated.
- `create_workflow` step 35b (`seed_PGC_Workflow.json`) rewritten: previously built one `|`-joined `intent_pattern` string, preferring user-typed phrases *or* (not *and*) `draft_workflow.intent_keywords` as a fallback. Now builds `intent_pattern_rows`, an array of `{pattern, intent_category, action_type, workflow_id, source}` objects — one per **distinct** phrase, deduped, unioning user-typed phrases (`source: 'user'`) **and** `intent_keywords` (`source: 'auto'`, no longer conditional on the user having typed nothing) **and** the truncated-userInput alias (`source: 'auto'`) **and** the workflow's own name (`source: 'name'`) — this is the explicit "fold `intent_keywords` into this model, eliminate the two-store split" instruction from the original scoping. Step 36 changed from a single-object `serv_insert` to a bulk `row: "{{intent_pattern_rows}}"` insert (established bulk-insert pattern from Track H/G1).
- `workflow_id` is computed directly in the step 35b `js_transform` from `local_state.registered_workflow.id` (already in scope from step 35) rather than via per-item template substitution inside the array — simpler and avoids relying on nested-object template resolution, which isn't an established pattern elsewhere in this codebase.
- `matchIntentMap` (`classify-intent-tiers.mjs`) needed no change — confirmed by direct test: it already regex-tests each row's `pattern` independently, so N single-phrase rows match identically to one joined-pattern row. `delete-workflow.mjs` needed no change either — its Step 5 `deleteRows` by `workflow_id` already removes *all* matching rows regardless of count.
- Data migration (same script): split the 3 existing workflow-linked joined-pattern rows (`import_budget_spreadsheet` id 349, `budget_vs_expense_report` id 351, `flashcard_quiz_session` id 341) into 12 single-phrase rows. Provenance can't be recovered exactly for pre-existing phrases — the phrase matching the workflow's own `intent_category` got `source: 'name'`; every other migrated phrase got `source: 'auto'` as a defensible default (going forward, new phrases are tagged precisely at creation time).
- `create_workflow` v77→v78 upserted live (pre-write simulation guard passed). 385/385 unit tests pass, including `workflow-schema.test.mjs`'s conformance check on the modified steps. Deployed (`sam build && sam deploy --no-confirm-changeset`) — bootstrap template change only, no runtime logic `.mjs` touched. Verified live: split rows match correctly via a direct `matchIntentMap` sanity check against real DB rows.

**A5 — Enum constraint rule**
- `design_workflow_process`: when designing a step that assigns an enum-constrained column (check constraint in domain_schema), include the exact allowed values in the step's `description` or `design_notes` so generate_workflow_steps can copy them into prompt_draft.
- `design_workflow_prompts`: when writing `prompt_text` for a step that assigns an enum-constrained column, copy the exact allowed values from domain_schema check constraints and explicitly forbid all other values.

**A6 — Reveal content rule in `design_workflow_dialogs`**
- `reveal.content` must reference a pre-formatted string key written by a preceding js_transform — never a raw array or object key. Directly referencing an array key renders as `[object Object]` at runtime.
- Add to design_workflow_dialogs reveal / reveals field instructions.

**A7 — Raw data parsing rule in `generate_workflow_steps`**
- When an llm_call step parses copy-pasted or scanned data, the input may originate from a pivot table or aggregated view where row group labels serve as dimension values for rows beneath them, not as data records. Copy-pasting may collapse the table structure so labels and column headers arrive as individual plain-text lines mixed with data.
- Where this pattern applies, prompt_draft should describe the un-pivot transformation in domain-specific language: group label levels adapted to actual domain column names and check constraint values from domain_schema. Avoid generic terms like "heading"/"sub-heading" in prompt_draft — prefer real column names where they can be inferred.
- Includes a state → city → person example showing pivot source, degraded arrival, and expected flat output. The parsing LLM should use judgment when input doesn't map cleanly; goal is the flattest representation the downstream serv_insert can consume.
- Language is intentionally softened (should/may/where applicable) since inference must adjust to actual data shape.

**C5 — Novia action-count reset on every gate resumption — DONE**
- Prompted by a user question about whether `max_actions_per_session` (default 5) resets when Novia is waiting on user input. - Fixed in `minds-eye.mjs`'s `handleGateResume`: every resume path now resets `minds_eye_action_count` — the `continue` gate (now unconditional, was previously gated behind a `resetActionCount` body flag that's now redundant since every gate resumption resets), the `followup` path (previously only reset `minds_eye_turn_count`), the action-gate **reject** path (previously didn't touch either counter at all), and the action-gate **approve** path (previously `session.minds_eye_action_count + 1` — an accumulating total; now hardcoded to `1`, i.e. reset-to-0-then-count-this-one-action). - **Separately verified (this was the deeper ask — guarding against runaway/silent cost explosion) that no endless-looping vector exists, independent of the change above:**
  - **Within one Lambda invocation**, `runReasoningLoop`'s `while (turnCost < prefs.turn_limit)` is provably bounded — every branch (read tool, write tool, gated tool, trigger tool, unknown action, `respond`) either increments `turnCost` by ≥0.5 or breaks out of the loop entirely; there is no path that loops without doing one or the other. Worst case (every tool call errors, at 0.5 cost each) is ~2x the nominal turn_limit budget (default 8 → ~16 LLM calls) before the loop is forced to stop — a real but bounded inefficiency, not unbounded risk. `ProcFunction`'s hard 240s Lambda timeout (`template.yaml`) is a second, independent backstop regardless.
  - **At the message/transport level**, `handler.mjs`'s `processSqsBatch` calls `deleteReceivedBatch(records)` unconditionally *before* any message-type dispatch — including `MINDS_EYE`/`MINDS_EYE_RESUME`. This means SQS's own `maxReceiveCount: 3` redrive-to-DLQ mechanism (`template.yaml`, `WorkflowQueue`) never actually triggers for these messages: a crash or timeout mid-processing leaves the message already deleted, so there is **no automatic retry at all** — the worst outcome of a Lambda crash is one wasted invocation, then silence (requiring manual noticing/restart), never a retry storm.
  - **Across invocations**, the only two ways to trigger another round of reasoning are a fresh `MINDS_EYE` message (new user prompt) or a `MINDS_EYE_RESUME` (a Slack button click or modal submission) — both require an actual human action in Slack. There is no scheduler, cron, or automatic re-trigger for Novia sessions, so genuinely unattended/silent indefinite looping is not possible under the current architecture.
  - **One related but distinct minor finding, flagged then and fixed in C6 below:** `turnCost` incremented by `0.5` on a tool error vs `1.0` on success — a persistently-failing agent got roughly double the intended number of LLM calls per invocation before `turn_limit` stopped it. Not what was intended (see C6).

**I3 — Uncertain-key cascade suppression — DONE**
- User caught a real false-positive risk: the smoke test does a single forward pass over the step array — it never unrolls loops. Flat-loop-pattern workflows (e.g. flashcard quiz: test each of 10 cards 3 times before advancing to the next subset, all subsets before a `human_gate`) depend on accumulator state a single pass can't reconstruct, so an accumulating `js_transform` can throw against placeholder mock data even when the workflow is correct.
- Before this fix: when a `js_transform` threw/timed out/void-returned, its `output_key` fell back to `{}` in `mockState` — a downstream step consuming that key via a bare `{{key}}` reference would then get shape-checked against `{}`, almost always failing, producing a **hard failure caused by an inconclusive upstream mock, not a confirmed defect**.
- Fix: `runJsTransformSmokeTest` now tracks a `uncertainKeys` Set — any `output_key` whose value came from the `{}` fallback (not a real computed result) is added to it. `checkStepInputContracts` skips (does not check, does not emit any issue) any field whose entire value is a bare `{{key}}` reference to an uncertain key.
