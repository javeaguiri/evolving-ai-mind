# Sprint 3 — Run Generated Workflows

**Goal:** Close the loop from workflow *generation* to workflow *execution*. Sprint 2 proved
`create_workflow` can generate a structurally valid workflow. Sprint 3 proves the generated
workflow actually runs correctly for users.

**Branch:** `sprint/03-run-generated-workflows`

---

## Scope

### Track A — Run the flashcard quiz (test vehicle)

The workflow generated by run 365 is registered in `PGC_Workflow`. Run it in Slack now.
Fix any runtime issues that surface — bad `serv_query` filter shapes, state keys not
available at the step that needs them, reveal field not rendering, iterator loop not
terminating on the correct condition, score not tracked correctly, summary not shown.

This is the acceptance gate for Sprint 2's real output. Generation passing L1+L2 simulation
is necessary but not sufficient — the workflow must actually run.

Acceptance criteria:
- [ ] Card set selection gate renders with live card sets from DB
- [ ] Quiz loop: each card shows front (question), reveal renders English definition via `task_card`
- [ ] User marks correct/incorrect; loop continues to next card in subset
- [ ] After subset completes, summary gate shows score
- [ ] End-to-end with no manual DB edits or workflow patches

### Track B — Domain context in create_workflow

Two coupled backlog items that must be fixed together:

1. **Fix `domain: null`**: `CREATE_WORKFLOW` SQS message currently passes only `userInput`.
   Resolve domain from `PGC_DomainHelp` or from the user's input before dispatch and
   include it in the SQS payload. The intent preprocessor in `classify-intent.mjs` already
   has the domain — wire it through.

2. **Inject `domain_schema` into generate_workflow_steps**: add a `serv_query` step before
   `generate_workflow_steps` that fetches `PGC_Schema` rows for the target domain and writes
   them as `domain_schema`. Update `generate_workflow_steps` prompt to accept and use
   `domain_schema` so the LLM knows what tables and columns the workflow can actually query.
   Same injection for `fix_workflow_routing` — the repair agent is currently blind to domain
   table structure.

Acceptance criteria:
- [ ] `domain` is non-null in create_workflow WorkflowRun inputs
- [ ] `domain_schema` is available in `local_state` when `generate_workflow_steps` fires
- [ ] Running create_workflow for a domain with a known schema produces steps that reference
  correct table names and column names without hallucination

### Track C — Deduplicate routing rules into PGC_SystemContext

`generate_workflow_steps` and `fix_workflow_routing` maintain parallel copies of CRITICAL
ROUTING RULES. Drift between them caused at least two routing bugs in Sprint 2. Fix:

1. Create a new `PGC_SystemContext` key (e.g. `workflow_routing_rules`) containing the
   canonical CRITICAL ROUTING RULES block.
2. Set `inject_for: ["generate_workflow_steps", "fix_workflow_routing"]` so both prompts
   receive it automatically.
3. Strip the duplicated block from both prompt texts, replacing with a note pointing to the
   injected context.

One upsert to `PGC_SystemContext` now fixes both prompts simultaneously. No more drift.

Acceptance criteria:
- [ ] CRITICAL ROUTING RULES exist in exactly one place (PGC_SystemContext)
- [ ] Both prompts receive the rules via inject_for, verified by checking prompt input in a
  diagnostic session
- [ ] A test create_workflow run generates steps with correct routing tokens on first attempt
